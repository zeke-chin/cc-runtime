# 工作区

同一个项目常常既在 Mac 上跑，也在开发机（linux/arm64）里跑。源码要两边共享，而依赖和构建产物（`node_modules`、`.venv`、`target`……）是平台相关的，不能共用同一个目录。本文说明 cc-runtime 怎么同时做到这两点。

## 两种用法

| | 纯 Linux | 同步副本（默认部署） |
| --- | --- | --- |
| 适用 | 项目只在开发机里运行和构建 | 同一个项目在 Mac 和开发机里都要运行 |
| 源码 | 一份，开发机直接挂载 Mac 的 workspace | 两份，Mutagen 双向同步 |
| 依赖 | 只有 Linux 一套 | Mac 一套，Linux 一套 |
| git 数据 | 在仓库原位 | 一份，移到两棵树之外 |
| 额外机制 | 无 | 同步会话、git 目录迁出、去重 |

纯 Linux 的做法：Mac 上的编辑器通过远程开发连进开发机（Cursor/VS Code 的 Remote-SSH、Zed 的远程开发），编辑、语言服务、终端和构建都在开发机里进行，依赖只装在开发机里。只在 Mac 上构建的项目（例如 Xcode 工程）同样不需要隔离。只要不需要在 Mac 本机运行项目，这种用法最简单。

本仓库的 `compose.yaml` 按同步副本部署。下面说明这种用法。

## 同步副本

```
WORKSPACE_DIR (Mac)           ⇄  Mutagen 双向同步  ⇄   RUNTIME_DIR/linux-workspace
Mac 的源码 + Mac 的依赖           依赖目录不参与同步         Linux 的源码副本 + Linux 的依赖
        │                                                        │ 挂载为每台开发机的
        │ foo/.git 是链接                                        │ /home/dev/workspace
        └────────────►  RUNTIME_DIR/git/foo.git  ◄───────────────┘ foo/.git 是同一个链接
                        唯一的一份 git 数据
```

### 为什么是两棵树

同一个路径要在两个系统上落到不同的存储，只有三种手段：

| 手段 | 结果 |
| --- | --- |
| 在该路径上挂载（逐个依赖目录挂卷） | 挂载必须在目录出现前建好，所以要扫描项目、预判目录、在新项目出现后重建容器；依赖目录是挂载点，`rm -rf node_modules` 会失败 |
| 让文件系统按名字路由 | 没有现成实现，要自写 FUSE 文件系统，所有源码读写经过它 |
| 放到另一棵树，源码靠同步 | 依赖目录按名字忽略即可，新项目自动生效 |

cc-runtime 选第三种。Linux 那棵树放在 Mac 的磁盘上（`RUNTIME_DIR/linux-workspace`），由开发机通过 bind mount 使用，而不是放在 Docker 卷里同步进容器：两端都在 macOS 上，变更检测是原生的，端点始终可用，数据在 Mac 上直接可见；代价是开发机内的文件读写要经过虚拟机边界，比卷慢。同步晚到或悄悄分叉是看不见的大代价，构建慢几秒是看得见的小代价，所以优先保证同步可靠。

- 副本不在 workspace 里面，同步的两端互不包含，正确性不依赖任何一条忽略规则。
- 所有开发机系统和架构相同，依赖可以通用，所以共用一份副本：只有一个同步会话，依赖装一次各机器都能用。不要在两台开发机上同时对同一个项目安装依赖。

### 同步会话

由 `cc-runtime sync create` 创建，名为 `linux-workspace`：

- 模式 `two-way-safe`：不会丢数据的冲突自动解决，其余记录下来等人处理，不覆盖任何一侧。
- 符号链接 `posix-raw`：原样同步，包括绝对路径和指向根目录之外的链接。
- 新建文件和目录的权限为 `0644`、`0755`；只同步可执行位。
- `--ignore-vcs`：真实的 `.git` 目录不同步，名为 `.git` 的符号链接照常同步（见下一节）。

### git 数据外置

两侧都要用 git，并看到同一个提交历史、分支和暂存状态。用文件同步复制 `.git` 不成立：`index` 里有本侧的文件状态缓存，另一侧随便一次 `git status` 都会改写它，两侧交错使用时会稳定地产生冲突，冲突后一侧的 git 状态悄悄过期。所以 git 数据只能有一份，两侧都直接读写它，由 git 自己的锁协调。

`cc-runtime git externalize <仓库>` 把仓库的 `.git` 目录移到 `RUNTIME_DIR/git/<相对路径>.git`，原位换成指向它的绝对路径链接。链接被同步到另一棵树；开发机把 `RUNTIME_DIR/git` 挂到同一路径，所以同一个链接在两边都能解析。git 的工作区是链接所在的目录，两边各自操作自己的文件，共用 `index`、`HEAD` 和对象库。

| 仓库状态 | 行为 |
| --- | --- |
| 已迁出，`.git` 是链接 | 两边都能用 git |
| 未迁出，`.git` 是目录 | 只在它所在的一侧能用 git；另一侧有源码，git 报「不是仓库」 |

未迁出是安全的默认状态：另一侧的 git 会明确报错，不会损坏数据。新仓库由定时任务 `externalize` 迁出。迁出时会跳过：

- git 自己的锁文件存在、正在接收对象、两分钟内有改动，或者还没有提交（可能正在 clone 或提交）；
- 含子模块或 `git worktree` 的仓库：子模块的 `core.worktree` 按 git 目录的真实路径解析，迁出后失效，之后的子模块命令又会写回只在一侧有效的路径；`worktree` 记录的绝对路径另一侧看不到，那一侧的 `git gc` 会把它当作可清理的删掉。这类仓库不迁出，在开发机里只有源码。

`cc-runtime git status` 报告每个仓库的状态和异常：链接断了、两个工作区共用一份 git 数据（`cp -R` 复制了项目）、git 数据没有工作区指向（删了项目）、链接目标和路径不符（改名或移动了项目）。`cc-runtime git restore` 把 git 数据移回 Mac 树的原位。

**使用约定：**

- 同一个仓库，同一时间只在一侧做 git 写操作（提交、切换分支、暂存、拉取）。只开着编辑器看不算。
- 一侧切换分支或拉取后，另一侧的 git 数据立刻是新的，文件要等同步到达（约一秒）。这期间不要在另一侧做 git 写操作；不确定时运行 `mutagen sync flush linux-workspace`。
- 复制项目用 `git clone`，不要 `cp -R`；已迁出的仓库不要再加子模块或 `worktree`，需要时先 `restore`。
- 删除项目后，对应的 git 数据要另外删除，`git status` 会列出来。

### 忽略名单

名单声明哪些目录属于每一侧私有，由三部分组成，`cc-runtime sync ignores` 列出完整结果：

| 来源 | 内容 |
| --- | --- |
| 项目（`sync-ignores`，入库） | 平台相关的依赖和构建产物：`node_modules`、`.venv`、`target`、`.next`、`.gradle` 等；各自生成的缓存：`__pycache__`、`.pytest_cache` 等。一般按名字在任意深度匹配，也可以写锚定路径。文件缺失时 `sync create` 和 `check ignores` 会报错 |
| 本部署 | 本仓库的 `dev-runtimes/`、`tailscale/state/`：各机器的家目录、密钥和登录状态 |
| 本机（`sync-ignores.local`，不入库） | 只属于这台 Mac 的条目：工作区里的大缓存、其他容器的数据库目录、名字不标准的虚拟环境等 |

`bin`、`obj`、`build`、`dist`、`vendor` 不在名单里：这些名字经常就是源码目录。名单在会话创建时固定，修改后要重建会话才生效，`cc-runtime status` 会提示名单和配置不一致。

`cc-runtime check ignores` 检查名单是否合理：

1. 两端和 git 目录互不包含，本部署的状态目录被忽略；
2. 没有被 git 跟踪的文件落在忽略名单里（那是不会同步的源码）；
3. 没有名字不标准的虚拟环境（会被同步）；
4. 任何容器以可写方式挂载的 workspace 内路径都被忽略。同步一个活的数据库目录会在写入中途复制它，Linux 侧的改动还会流回去。

### 去重

Mutagen 把同步的每个文件写成新数据，所以副本在磁盘上另占一份。去重把两侧同一路径、内容相同的文件变成文件系统的克隆，共用数据块：

- macOS（APFS）：把 Mac 侧文件 `clonefile()` 到同步树之外的临时位置，再次核对两侧文件没被改动，然后改名覆盖 Linux 侧的文件，保留它原来的权限和修改时间。
- Linux（Btrfs、XFS、bcachefs、ZFS 2.2+）：用 `FIDEDUPERANGE`，内核在加锁状态下比较内容，相同才共享，文件不被替换。
- 不支持克隆的文件系统（ext4、NTFS）：报错退出，不做任何改动。

只处理不小于 1 MiB、两侧 24 小时内都没改过、内容相同的文件；已经共享的文件记在状态里，下次跳过。Mutagen 不会维持共享：文件只要改了一点，另一侧就会被整份重写。所以去重由定时任务每天运行一次，白天改过的文件暂时各占一份。

APFS 的本地快照（Time Machine 每小时建一个）会继续引用被替换掉的旧数据块，回收的空间要等快照过期后才会出现在 `df` 里。去重不改变 Mac 侧的任何文件，也不需要暂停同步。

### 定时任务

任务登记在 `internal/jobs/jobs.go`。launchd 直接调用安装好的二进制 `~/.local/bin/cc-runtime job run <任务>`，并通过 `CC_RUNTIME_ROOT` 传入仓库位置，所以任务不受仓库当前检出的分支或开发环境影响；重新运行 `scripts/install.sh` 后，下一次运行就会用上新版本。每次运行都会记录结果，在 `cc-runtime status` 里显示：

| 任务 | 时间 | 作用 |
| --- | --- | --- |
| `dedupe` | 每天 04:00 | 去重。同步会话不健康时跳过 |
| `externalize` | 每 5 分钟 | 迁出新仓库的 git 数据 |

`cc-runtime schedule install <任务>` 安装，`schedule list` 查看，`job log <任务>` 看历史。只有 macOS 有 `schedule`；Linux 上用 systemd timer 运行 `job run`。

## 代价与限制

- **开发机内的文件读写变慢。** 依赖和项目文件经过虚拟机边界（OrbStack 的 virtiofs）。合成测试中小文件操作比卷慢 6 到 10 倍；真实项目在缓存已热时，Node 安装 3.1 s 对 1.0 s、构建 7.3 s 对 6.4 s，Rust 构建 22.5 s 对 21.3 s。
- **换侧后第一次 git 命令要重读文件。** `index` 只有一份，而两棵树里同一个文件的修改时间不同（Mutagen 不保留修改时间）。1 万个文件的仓库约 0.6 到 0.8 秒，之后的命令约 0.05 秒。
- **同步延迟。** 一般在 0.5 秒以内；切换相差上千个文件的分支，另一侧约 1 秒后追平。
- **冲突要人处理。** 同一文件在同步窗口内被两边同时修改时会被标记，不会自动合并；`status` 会显示。
- **重命名或删除项目时，另一侧可能留下旧目录。** 另一侧这个目录里如果有被忽略的内容（依赖），会话会报冲突，旧目录连同源码留在那一侧；删掉残留后冲突自动消失。重命名后依赖要在新路径重新安装。
- **同步进程要常驻。** Mac 上的 Mutagen 守护进程应注册为登录后启动（`mutagen daemon register`）。它停止时两侧各自继续工作并逐渐分叉，`status` 会报出来。
- **规则没有消失。** 仍然要维护一份忽略名单，只是从「按项目预判每个目录」变成「十几个名字持续生效，并且有检查」。

## 没有采用的方案

| 方案 | 原因 |
| --- | --- |
| `.git` 随源码一起同步 | 交错使用时稳定地产生 `index` 冲突，冲突后一侧的 git 状态悄悄过期 |
| git 数据留在 Mac 仓库原位，Linux 树链接过去 | 可行，但开发机要可写地挂载整个 Mac workspace，Linux 侧的链接和新仓库的搬迁都要靠脚本逐个维护 |
| 只同步 `.git` 的一部分（`index` 每侧一份） | 一侧提交后，另一侧的暂存区过期，显示一份反向的改动 |
| 副本放 Docker 卷，同步进容器 | 依赖读写是原生速度，但同步要经过容器内代理、Linux 端靠轮询检测变化、端点依赖容器运行。保留为依赖速度不可接受时的后备 |
| 每台开发机各一份副本 | 开发机系统和架构相同，依赖没有差别；分开只会让副本、会话和安装次数随机器数增加 |
| 工具级重定向（`UV_PROJECT_ENVIRONMENT`、`CARGO_TARGET_DIR`） | Node 没有等价机制，`node_modules` 必须位于项目旁 |
| overlayfs（Mac 树做下层） | 源码和 `.git` 的写入也会落在上层，到不了 Mac |
| 硬链接代替克隆去重 | 一侧改动会立即改到另一侧，等于绕过同步 |
