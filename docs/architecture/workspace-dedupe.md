# 副本去重：用文件系统克隆回收重复空间

状态：已实现（2026-11-13），脚本为 `scripts/workspace-dedupe.py`。属于 [依赖隔离](dependency-isolation.md) 方案 2 的配套设计。

## 结论

方案 2 让 Mac 的 workspace 和 Linux 副本各占一份磁盘空间。每天定时跑一次去重：把 Linux 副本里和 Mac 侧内容相同的文件，替换成 Mac 文件的克隆，让两者共用同一批数据块。白天改过的文件暂时各占一份，到下一次去重时回收。

- 同步照常实时进行，去重不改变任何文件的内容，只改变文件在磁盘上的存放方式。
- 依赖目录（`node_modules`、`.venv`、`target` 等）两侧本来就不同，不参与去重。
- 只改 Linux 副本，从不改 Mac 侧的文件。

## 要解决的问题

2026-11-12 首次同步后，Linux 副本 `~/.cc-runtime/linux-workspace` 占用约 65 GB（69 GB 逻辑大小，约 26 万个文件）。其中大部分是不常变的大文件，例如 `github_work/shopify-lens/data/oss-history`（32 GB 数据）和 `models`（3.8 GB）。这些文件两侧内容完全相同，却各占一份空间。

## 原理

### 内容相同不等于共用空间

写时复制的文件系统支持「克隆」：新文件直接指向原文件的数据块，不复制数据；以后哪一侧改了某个块，只有那个块会被另写一份。克隆出来的两个文件互相独立，改一个不会影响另一个。

但两个文件只有**通过克隆创建**，才会共用数据块。文件系统不会检查内容，所以先新建一个文件、再写入同样的字节，得到的是一份全新的数据，哪怕内容和别的文件一模一样。APFS、Btrfs、XFS 都没有实时去重（ZFS 有，但代价很高，一般不开）。

### 为什么同步之后共享会消失

Mutagen 同步一个改动时，在另一侧新建一个临时文件，用旧版本里没变的部分加上传过来的改动拼出新内容，写完后改名替换旧文件。它不知道对侧有一个可以直接克隆的文件，所以：

- 首次同步时，Linux 副本里的每个文件都是新写的一份。
- 去重之后，某个文件只要有一侧改了，哪怕只改几个字节，Mutagen 也会在另一侧整份重写，这个文件的共享就没了。
- 同步完成后两侧内容又一样了，但要再做一次去重，才会重新共用数据块。

所以 Mutagen 不会主动维持共享，要靠定期去重把它找回来。

### 实测（2026-11-13，Mac，APFS，Mutagen 0.18.1）

在临时目录里建一个和真实会话参数相同的会话，放入 4 个 256 MB 的随机文件和 200 个小文件，同步后对 Linux 一侧做克隆去重：

| 检查 | 结果 |
| --- | --- |
| 回收的空间 | 1 GB 里回收约 1007 MB |
| Mutagen 的反应 | 没有冲突，也没有把这次替换同步回去；Mac 侧文件的修改时间和 inode 都不变 |
| 去重后的双向同步 | 正常 |
| 克隆的独立性 | 改一侧的克隆文件不影响另一侧，改动照常经同步传过去 |
| 去重后改动大文件 | 在 256 MB 的文件里就地改 4 个字节，Mutagen 在另一侧整份重写，这 256 MB 的共享随之消失 |

## 设计

### 什么时候运行

每天一次，在凌晨使用者不工作的时候。Mac 上用 launchd 任务，Linux 上用 systemd timer。

磁盘占用因此有了上界：两份源码只多占「上次去重之后改过的文件」那一部分，加上两侧各自的依赖目录。

### 处理哪些文件

逐个处理两棵树里**同一相对路径**下的文件对，满足下面全部条件才处理：

1. 两侧都是普通文件，不是链接或目录。
2. 不在同步的忽略名单内（与 `scripts/workspace-sync.py` 共用同一份名单）。被忽略的路径两侧本来就不同，也不保证同名就是同一个东西。
3. 大小相同，并且不小于阈值（默认 1 MiB）。小文件数量多、总量小，去重的收益抵不上逐个比较的开销。
4. 两侧最近 24 小时内都没有被修改过（看修改时间和状态改变时间）。最近还在改的文件，大概率很快又会被改，而且这样能避开正在写入的文件。
5. 内容逐字节相同。

不在同一路径下的相同文件（比如两个项目里的同一个大文件）不处理。只做路径一一对应的配对，规则简单、结果可预期。

### 状态文件：避免每天重读全部数据

已经共享的文件，下次就不需要再比较。脚本把每个已处理的文件对记在 `~/.cc-runtime/dedupe-state.json` 里，记录两侧的 inode、大小和修改时间。下一次运行时，两侧这三项都没变的文件对直接跳过。没有这个记录，每天都要把几十 GB 的数据读两遍。

状态文件丢失或损坏时，下一次就全部重新比较一遍。结果仍然正确，只是慢一些。

### macOS（APFS）：克隆后替换

macOS 没有「内核比较后再合并」的接口，只能先克隆、再替换，由脚本自己保证安全。对每个文件对：

1. 记下两侧的 inode、大小、修改时间、状态改变时间。
2. 逐字节比较两侧内容。
3. 用 `clonefile()` 把 Mac 侧的文件克隆到 `~/.cc-runtime/dedupe-tmp/` 下的临时名。这个目录和副本在同一个卷上，所以第 6 步跨目录改名仍然是原子操作；它又在两棵同步树之外，所以 Mutagen 看不到临时文件。如果放在 Linux 文件旁边，Mutagen 可能在改名之前就把临时文件同步到 Mac 侧。
4. 把临时文件的权限和修改时间设成 **Linux 侧原文件**的值，而不是 Mac 侧的。容器里 git 索引的文件状态缓存记录的是 Linux 侧的值，这样能少一次失效。
5. 再记录一次两侧的元数据，和第 1 步对比。任何一项变了，就删除临时文件、跳过这一对。
6. `rename()` 临时文件，覆盖 Linux 侧的原文件。

第 5 步之后、第 6 步之前，仍有一个很短的窗口。如果有程序恰好在这段时间里写这个文件，它写入的内容会被克隆覆盖，而这个覆盖又会被同步回 Mac。要求两侧 24 小时内都没改动过（条件 4），就是为了让这种情况在实际中不会出现。

已知影响：替换后 Linux 侧文件的 inode 变了。git 默认比较 inode，所以容器里下一次 `git status` 会重读这些文件，一天一次，可以接受。

### Linux（Btrfs、XFS、bcachefs、ZFS 2.2+）：内核去重

用 `FIDEDUPERANGE` ioctl（`duperemove` 用的就是它）。内核会锁住两个文件比较内容，只有确实相同才让它们共用数据块。文件本身不被替换，inode、修改时间都不变，也就没有上面那个竞态窗口。

### 不支持克隆的文件系统

ext4、NTFS 等不支持克隆。脚本启动时先确认两棵树和工作目录 `~/.cc-runtime` 在同一个文件系统上，再在工作目录里用两个临时文件探测一次（不在同步树里，免得探测文件被同步出去）。不支持就明确报错退出（退出码 3），不做任何改动。

### 可见性

- 每次运行的统计（处理了多少对、跳过多少、回收了多少字节、耗时）追加到 `~/.cc-runtime/dedupe.log`。
- 去重后 `du` 仍会把共享的文件按两份计算，要看 `df` 的剩余空间才知道实际占用。日志里记录运行前后 `df` 的差值。
- `--dry-run` 只列出会处理的文件和预计回收的空间，不做改动。

### 本地快照会推迟空间的释放

APFS 的本地快照（Time Machine 每小时建一个）会继续引用被替换掉的旧数据块，这些块要等快照删除后才会释放。在 Time Machine 里排除 `linux-workspace` 不影响本地快照：本地快照是对整个卷做的，排除只作用于备份到外部目标的那部分。

2026-11-13 第一次在真实副本上运行时，Linux 副本已经被 `com.apple.TimeMachine.2026-11-13-195207.local` 这个快照捕获，所以 63 GB 共享完成后 `df` 没有变化，要等这个快照被 Time Machine 清理（一般在成功备份之后，最长 24 小时，磁盘紧张时更早）才会释放。临时目录里的端到端测试没有这个问题，因为那些文件是在最近一次快照之后才创建的。

所以：

- 回收的空间会滞后释放，最多晚一个快照的保留期。磁盘占用仍然有上界，只是晚一点兑现。
- 日志里的 `free_gained_bytes` 只反映当时 `df` 的变化，有快照时接近 0，不能当作回收量。判断去重效果看 `shared_bytes` 和 `already_bytes`。
- 想立刻释放，可以手动删除那个快照（`tmutil deletelocalsnapshots <日期>`），代价是少一个本地还原点。脚本不会删除快照。

### 和同步会话的关系

- 去重期间不需要暂停同步会话。实测 Mutagen 会看到替换，但发现内容没变，不会同步任何东西，也不会报冲突。
- 去重运行前检查会话健康（`workspace-sync.py status`）。会话有冲突或者没在运行时不去重，因为这时两侧内容可能本来就该不同。

## 没有采用的做法

| 做法 | 不采用的原因 |
| --- | --- |
| 硬链接 | 两个路径指向同一个文件，一侧改了另一侧立即跟着变，等于绕过了同步；并且很多工具会就地写文件，会同时改到两侧 |
| 把同步改成每天一次 | 源码要实时共享。git 数据只有一份，而源码要等同步，一侧提交后另一侧的 `git status` 会一整天显示改动，容易把旧文件提交回去 |
| 实时去重（监听文件事件） | 改动刚发生的文件最可能马上再改，实时去重收益小，还会和正在写入的程序竞争。每天一次已经足以控制磁盘占用 |
| 让 Mutagen 用克隆写文件 | Mutagen 不支持，而且它的传输模型是按块重建文件，不知道对侧的文件路径 |
| 去重 Mac 侧自己的重复文件 | 不在本设计范围内，也不应改动使用者的 workspace |
| 把大数据目录加进忽略名单 | 可以和去重同时使用。只适用于容器里确实不需要的目录，由使用者逐个决定 |

## 使用

```bash
python3 scripts/workspace-dedupe.py run --dry-run   # 只统计会共享多少，不改动
python3 scripts/workspace-dedupe.py run             # 去重一次
python3 scripts/workspace-dedupe.py install         # macOS：装 launchd 任务，每天 04:00 运行
python3 scripts/workspace-dedupe.py uninstall
```

- `--min-size`（默认 1 MiB）和 `--quiet-hours`（默认 24）可以调整筛选条件。
- 会话有冲突或没有运行时不去重，退出码 2；文件系统不支持时退出码 3；有文件出错时退出码 1，其余文件照常处理。
- 运行时的文件都在 `~/.cc-runtime/` 下：状态 `dedupe-state.json`，日志 `dedupe.log`（每次一行 JSON），launchd 的输出 `dedupe.launchd.log`，临时目录 `dedupe-tmp/`，锁 `dedupe.lock`。
- 日志里的 `free_gained_bytes` 是运行前后 `df` 可用空间的差值，也就是实际回收的空间；`shared_bytes` 是本次新共享的文件大小之和；`already_bytes` 是此前已共享、本次跳过的部分。
- Linux 上没有 `install`，用 systemd timer 每天运行 `run`。
