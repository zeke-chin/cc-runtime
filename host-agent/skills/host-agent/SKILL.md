# Mac 任务服务

调用方负责开发和任务统筹，通过 `host-agent` 委派需要 Mac 执行条件的步骤，取得证据后继续完成整体任务。

## 分工与触发边界

需求分析、方案设计、项目源码与测试修改、可复用脚本、文档、可直接运行的验证，以及授权范围内的 Git 操作，默认由调用方完成。Swift／iOS 项目的代码编辑也遵循这一分工。

先判断具体步骤依赖什么执行条件，再决定是否委派：

- Mac 工具链或设备：Xcode／Apple SDK 构建、模拟器、签名、连接 Mac 的真机安装与验证。
- Mac 桌面或会话：需要实际操作 Mac 应用，或依赖 Mac 上的浏览器登录会话、Computer Use 工具。
- Mac 专有访问条件：调用方无法访问、而 Mac 可访问的服务器网络、凭据或服务。此类现场查询、日志采集、验证及已获授权的部署可以委派。

对于已知仅由任务服务侧访问的内网或远端服务器（可在用户常驻指令或项目说明中声明），相关查询、日志采集、验证及已授权部署可直接委派；访问失败或条件变化时再核查，无需每次在调用方重试连接。

按实际工具或访问依赖分工；仅因任务涉及 Apple、浏览器、SSH 或耗时较长，不构成委派理由。同一验收目标下、均依赖 Mac 的现场步骤可以合并，开发工作保留在调用方。Mac 可在任务范围内自主补充查询、只读分析源码、编写临时诊断脚本并提出修复建议，无需逐条命令往返。

Mac 默认不修改项目源码、测试、可复用脚本或项目配置，也不代做提交、推送、合并或切分支；可以只读检查 Git 状态、差异和历史。构建生成物和临时诊断产物不属于项目开发；按已授权部署流程更新服务器运行文件也不等于在服务器直接改业务逻辑。需要代码修复时由调用方接回，除非用户明确指定由 Mac 承担该项修改，并在交接中写明范围。

## 检查服务

确定需要委派后，执行 `host-agent capabilities`，检查 `online`、`projects` 和 `active_task`。服务在线不代表目标服务器、设备或应用已经可访问。

- `online=false`：服务未就绪或心跳过期。说明实际状态，不把排队成功当作正在执行。
- `computer_use=advertised` 仅表示服务提供该工具。具体应用授权、浏览器接入、手机连接等仍需实际验证。
- 在任务所属项目目录执行提交。客户端根据当前目录的 Git 仓库根目录，从 `project_paths` 中自动匹配项目（包含 Mac 路径与调用方 `client_paths`），子目录属于同一仓库。没有映射或匹配多个项目时，先配置唯一的项目映射再提交。

## 提交

在项目目录获取完整提交号，任务文本写清：

- 必须使用 Mac 的工具、设备、会话或访问条件。
- 本轮目标、验收条件、必要背景及已有有效结果；有现成命令或脚本时一并提供。
- 允许的现场操作与停止条件；发现需要修改项目代码的问题时返回诊断和建议。
- 应返回的实际命令、退出码、日志／截图／查询证据及未完成项。

沿用用户已经明确的授权，准确写入 `--authorization`，无需重复请求相同授权；不把交接说明中的“下一步”当作授权。

提交前由调用方 Agent 理解任务目标，将核心动作与对象概括为五字以内的完整短语，通过必填的 `--title` 传入。例如“检查会员页订阅按钮、续订状态和布局”概括为“订阅验收”，“查清上传失败原因并重跑上传”概括为“上传排障”。短名独立表达任务含义，不截取正文前几个字；续接任务按本轮目标重新概括。

```bash
host-agent submit --title "布局验收" --commit "$(git rev-parse HEAD)" \
  --task "需要 Xcode 和 iOS 模拟器。运行 iOS 构建和 AppLayoutTests，确认实际执行数量大于零；返回命令、退出码、日志和截图。发现源码问题时返回诊断与修复建议，由调用方修复后再复验。" \
  --authorization "仅本地构建、模拟器测试与诊断；不修改项目源码。"
```

长文本使用 `--task-file /path/to/task.txt`，避免 Shell 引号改变内容。`--commit` 省略时读取当前目录的 HEAD；服务遇到提交不一致会失败，不会切分支。提交号相同不代表工作区内容未变，未提交修改也可能影响执行结果。

`--project` 仅用于显式核对，必须与当前仓库自动匹配的项目一致。跨项目任务先切换到目标项目目录；续接任务也在原任务所属项目内提交。目录映射失败时补齐映射，不通过切到无关项目或复用其别名绕过检查。Herdr 窗口归属由匹配到的 Mac 项目目录决定。

提交后保存 `task_id`。执行期间暂停相关代码写入、切分支和提交；仍可处理不相干的工作。服务只能串行化自己的任务，不能锁住其他编辑器或 Agent。

## 跟进

```bash
host-agent status TASK_ID
host-agent result TASK_ID
host-agent message TASK_ID "补充验收条件……"
host-agent cancel TASK_ID
```

按任务耗时每 5–15 秒查询一次，不要忙循环。`message` 只用于运行中的任务；提交控制请求后，通过 status 中的 controls 确认是否 delivered/rejected。`cancel` 是停止请求，直到状态终结才算结束，也不会回滚已有改动。

状态为 `waiting_for_approval` 或 `waiting_for_input` 时，向用户展示 pending 中的具体请求和 token，等待用户通过服务管理入口答复。不要自行创建审批结果或通过补充消息冒充用户批准。

任务结束后，需要延续之前的任务上下文时，重新 submit，并增加 `--after TASK_ID`。新任务仍须核对当前提交和授权。不要因等待时间较长而重新提交同一个任务；先查询已有 ID。

## 解释结果

只有 `completed` 加上结果中的实际验证证据才能支持“已完成”。`failed`、`interrupted`、`unknown` 都需要报告原因；`unknown` 表示无法确认执行是否停止，服务会阻止后续执行，恢复连接并核对旧任务后再继续。

Mac 完成诊断并交回代码问题，只表示本轮诊断结束，不能据此宣称缺陷已修复或整体验收通过。调用方阅读证据、判断原因并修改代码与测试；确认上一任务已终结后再恢复相关写入，完成可直接运行的验证，再提交必要的 Mac／服务器复验。每轮仍保留开发与统筹责任。

日志位于 `/run/host-agent/jobs/TASK_ID/events.jsonl`，产物位于同目录的 `artifacts/`。使用服务返回的可读取路径获取文件，如返回的是执行目录中的路径，则在此产物目录下查找对应文件。根据实际证据报告服务执行结果，不把提交成功当作执行成功。最终向用户报告已完成内容、测试证据、改动、产物及仍需处理的事项。
